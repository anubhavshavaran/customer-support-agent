# AmazonHelp support agent report

## Problem framing

The goal is a conservative first-line Twitter support assistant for AmazonHelp. Good means: it recognizes the customer's support need, drafts a short response that is visibly supported by similar AmazonHelp resolutions, and sends account-specific or risky cases to a human. The system is not an order lookup tool, does not access customer data, does not promise refunds or delivery dates, and does not try to solve every language or product domain in the dataset.

The dataset is converted into direct cases by joining each AmazonHelp outbound tweet to its inbound parent. This produces historical customer messages paired with the actual brand response. The project uses eight intents derived from the English AmazonHelp slice: delivery, order changes, returns/refunds, account/membership, device/app problems, billing/payment, product information, and general complaints.

## Evaluation design

`data/processed/golden_set.csv` contains 200 examples. I sampled the direct cases with a fixed seed, selected examples evenly across the eight intents, read each message against the intent handbook, and recorded an expected routing action. The set is removed from the training corpus. This is a single-reviewer gold set, not a claim of inter-annotator reliability; a next iteration should add a second labeler and adjudication.

The evaluation compares:

1. Majority class: always predicts the most frequent training intent.
2. Keyword rules: the compact intent handbook.
3. TF–IDF logistic regression: word and bigram features with class balancing.

The agent adds nearest historical resolution retrieval and escalation. `metrics.json` is the generated source of truth for the current run.

## Results

The exact values below are generated by `python -m src.main run` and are kept in `data/processed/metrics.json`.

| Model | Accuracy | Macro F1 | Balanced accuracy |
|---|---:|---:|---:|
| Majority | 0.125 | 0.0278 | 0.125 |
| Keyword rules | 0.740 | 0.7342 | 0.740 |
| TF–IDF logistic regression | 0.925 | 0.9250 | 0.925 |

The complete agent has 0.925 intent accuracy, 0.925 routing accuracy, a 0.770 auto-handled rate, and 0.935 accuracy among auto-handled examples. Mean reply quality is 4.162/5: relevance 3.990, groundedness 3.830, helpfulness 3.600, tone 4.390, and safety 5.000. The offline judge's quadratic weighted kappa against 30 manually reviewed calibration examples is 0.121, so I do not treat the judge as a substitute for human review.

## Reply judge

Every draft is scored from 1–5 on relevance, groundedness, helpfulness, tone, and safety. Groundedness means that the reply's concrete action is supported by the retrieved historical reply; safety penalizes pretending to inspect private account or payment information. The default scorer is offline and reproducible. The optional LLM judge receives the same customer message, predicted intent, route, draft, and top historical examples and must return JSON with the same dimensions. `judge_calibration.csv` records 30 development examples with human overall labels and the judge score; the harness reports quadratic weighted kappa.

The calibration is deliberately small and should be treated as a guardrail, not proof that an LLM judge is unbiased. A production review would blind two human raters to the model and report agreement before trusting the judge at scale.

## Top failure modes

1. Product/device overlap. “I have the app to watch movies & tv on my Samsung TV, is there an app for the music version of prime for Samsung TV?” was predicted as `device_app_issue` instead of `product_information`. The model sees “app” and “TV” before the actual availability question.
2. Refund versus order change. “I returned the order ... a refund has not been initiated” was predicted as `order_change` instead of `return_refund`. The word “order” is more common than the resolution state; refund status should take precedence.
3. Delivery versus order change. “I have placed an order ... Not received order ... Estimated Delivery Date ... today is 30Nov” was predicted as `order_change` instead of `delivery_issue`. A dedicated order-status class and thread context would help.
4. Membership complaints. “Amazon fails to bind customers and started cancellation of membership itself” was predicted as `general_complaint` instead of `account_membership`. Complaint tone hides the actionable membership event.
5. Language and short context. “Using my own brain, I selected a different language and after multiple attempts I was able to reach a human voice” was predicted as `device_app_issue` instead of `general_complaint`. The single-tweet model cannot reliably resolve language, sarcasm, or missing context.

## What is misleading about my headline number?

The golden labels come from a compact handbook applied by one reviewer, so classifier accuracy partly measures agreement with that handbook rather than real customer understanding. The sample is balanced by intent while traffic is not, and the set contains only English-like direct replies from one brand. Retrieval also benefits from repeated support boilerplate. Finally, reply quality is judged against historical behavior, which can reward a polite handoff even when a real customer would need a more specific answer. These results support a prototype and an audit trail, not autonomous production support.

## One more week

I would add a second annotator and 50 deliberately hard counterexamples, evaluate by time-based split, preserve conversation context, tune escalation thresholds for high precision on auto-handling, and run a red-team review for account security, payments, refunds, and personal data. I would also compare extractive drafts with an LLM rewrite only when the retrieved evidence passes a strict supportability check.

## Decision log

- Chose AmazonHelp because it has a large number of directly linked historical resolutions.
- Used direct parent links instead of pretending that every tweet row is a complete conversation.
- Kept eight intents so the classes remain actionable and auditable.
- Used the keyword handbook as a baseline and as the initial labelling protocol.
- Held out the golden examples before fitting the model or retriever.
- Used a fixed seed so the gold set and headline results are reproducible.
- Used TF–IDF instead of embedding downloads so the required run works offline.
- Used historical response retrieval as the default draft to limit unsupported claims.
- Escalated unknown charges and account-security signals regardless of classifier confidence.
- Added a minimum evidence threshold because a confident classifier can still retrieve a poor match.
- Reported macro F1 and balanced accuracy because the brand's intent distribution is uneven.
- Included a majority baseline so the model cannot hide behind a favorable class mix.
- Included a calibration sample because judge scores are not ground truth.
- Kept OpenAI generation and judging optional rather than making the headline run depend on an API key.
